# Post-EXP-004 Comparative Design Audit

Inspection date: **2026-10-05**. GTC-HD-Lab: `main`, `836751bc775abcbf1ecc102a43ea92a72de8fc37` before this documentation change.

**GTC-HD INFERENCE / recommendation:** build one bounded, offline native-sample replay with a frozen source-selection and enhancement preview. First reconstruct an explicitly owned interval from captured operands, controls and history; then let an author select a contributing source occurrence and adjust a restrained glow. This tests whether semantics improve an actual visual interaction without requiring persistent asset identity, physical depth, a complete frame interface or a full Studio. It is a proposal, not implementation authorization or an architecture decision.

## 3. Which mechanisms transfer?

### A. bsnes-hd: enhanced sampling still needs native inputs and their lifetimes

**SOURCE OBSERVATION:** `Line::cache` snapshots per-line IO/CGRAM; `Line::flush` prepares Mode 7 HD state and renders queued lines. `writeVRAM` flushes queued rendering before mutating VRAM. Thus the rendering boundary combines cached raster state with access to mutable graphics memory protected by ordering; it is not an independent, permanently owned scene packet. See [line.cpp](https://github.com/DerKoun/bsnes-hd/blob/fc26b25ea236f0f877f0265d2a2c37dfd93dfde9/bsnes/sfc/ppu-fast/line.cpp), [io.cpp](https://github.com/DerKoun/bsnes-hd/blob/fc26b25ea236f0f877f0265d2a2c37dfd93dfde9/bsnes/sfc/ppu-fast/io.cpp).

**SOURCE OBSERVATION:** `cacheMode7HD` groups compatible Mode 7 lines and checks coefficient conditions for perspective handling. `renderMode7HD` uses matrix/center/scroll/repeat/flip state, neighboring-line interpolation, VRAM map/texel reads, CGRAM and native priority/window context for higher-resolution sampling. `renderMode7` routes to this path only under its scale/mosaic conditions; otherwise its ordinary fast-PPU Mode 7 path remains. That is a concrete fallback branch, not proof that every HD option is cycle-PPU equivalent. See [mode7hd.cpp](https://github.com/DerKoun/bsnes-hd/blob/fc26b25ea236f0f877f0265d2a2c37dfd93dfde9/bsnes/sfc/ppu-fast/mode7hd.cpp), [mode7.cpp](https://github.com/DerKoun/bsnes-hd/blob/fc26b25ea236f0f877f0265d2a2c37dfd93dfde9/bsnes/sfc/ppu-fast/mode7.cpp).

**SOURCE OBSERVATION:** game loading obtains `.bso` settings, and `Program::hackCompatibility` applies compact per-game overrides over configured defaults through emulator settings. An author can supply overrides; a game patch is not intrinsic to this settings mechanism. Native register/memory state, cached lines and configuration survive until their consumers run; writes/flushes and subsequent game/configuration loads define relevant boundaries. There is no persistent game-entity identity here. See [game.cpp](https://github.com/DerKoun/bsnes-hd/blob/fc26b25ea236f0f877f0265d2a2c37dfd93dfde9/bsnes/target-bsnes/program/game.cpp), [hacks.cpp](https://github.com/DerKoun/bsnes-hd/blob/fc26b25ea236f0f877f0265d2a2c37dfd93dfde9/bsnes/target-bsnes/program/hacks.cpp), and the [documented overrides](https://github.com/DerKoun/bsnes-hd/blob/fc26b25ea236f0f877f0265d2a2c37dfd93dfde9/README.md).

**GTC-HD INFERENCE:** the nested subpixel loops make higher sampling cost plausible, but no measured cost is established here. Fast-PPU memory access and Mode 7 matrices do not transfer from EXP-004 winner records. **Consequence:** defer independent Mode 7 resampling; a later consumer must either own the needed bytes/state or document a synchronization contract. Never read later emulator VRAM and call it the earlier sample's immutable source.

### B. Mesen: replacement rules work because capture, context and precedence are explicit

**DOCUMENTED CLAIM / lineage:** the [archived Mesen2 README](https://github.com/SourMesen/Mesen2/blob/b9fa69ddc6d0a331fb103fdb5eef6904305703c2/README.md) directs continuation to CE. The [legacy HD-pack documentation](https://www.mesen.ca/docs/hdpacks.html) describes version 105, tile rules, contextual conditions, ordered matches and a record/edit-image workflow. CE's inspected [HdNesPack.h](https://github.com/nesdev-org/MesenCE/blob/a60e79feb4d6dcced5922d636f9211837d01e381/Core/NES/HdPacks/HdNesPack.h) declares version 109. Corresponding files were compared across both pinned trees; they are not all identical. The following mechanism is **CE at the pinned revision**, not a claim that legacy documentation fully specifies current behavior. It lives under `Core/NES/HdPacks`; Mesen's broader SNES support does not establish SNES HD-pack support.

**SOURCE OBSERVATION — producer/lifetime:** `StoreTileInformation`, `StoreSpriteInformation` and `DrawPixel` collect CHR location/content, palette, flip/offset/priority and sprite alternatives. CHR-RAM tile bytes are copied. `OnBeforeSendFrame` swaps HD screen buffers and snapshots watched memory values for conditions. `HdTileKey` compares palette plus ROM tile index or 16-byte RAM tile content, rather than trusting only a hash. This data is richer than GTC-HD's winning fetch token and raw color. See [HdNesPpu.h](https://github.com/nesdev-org/MesenCE/blob/a60e79feb4d6dcced5922d636f9211837d01e381/Core/NES/HdPacks/HdNesPpu.h), [HdNesPpu.cpp](https://github.com/nesdev-org/MesenCE/blob/a60e79feb4d6dcced5922d636f9211837d01e381/Core/NES/HdPacks/HdNesPpu.cpp), [HdData.h](https://github.com/nesdev-org/MesenCE/blob/a60e79feb4d6dcced5922d636f9211837d01e381/Core/NES/HdPacks/HdData.h).

**SOURCE OBSERVATION — matching/consumer:** loader initialization builds ordered rule lists. `GetMatchingTile` searches exact and fallback/default-key buckets, then returns the first rule whose conditions pass. Wildcard lookup is conditional on bucket lookup failure; it is not an unconditional second chance after all rules in an existing exact bucket fail. `GetCachedMatchingTile` resets its local cache at tile boundaries; spatial sprite conditions can disable that cache. `GetPixels` uses original NES colors when no replacement supplies the relevant pixel, although the optional `DontRenderOriginalTiles` policy can suppress the ordinary background fallback. Faithful fallback must therefore be a deliberate product rule, not assumed from the existence of a replacement API. See [HdPackLoader.cpp](https://github.com/nesdev-org/MesenCE/blob/a60e79feb4d6dcced5922d636f9211837d01e381/Core/NES/HdPacks/HdPackLoader.cpp), [HdNesPack.cpp](https://github.com/nesdev-org/MesenCE/blob/a60e79feb4d6dcced5922d636f9211837d01e381/Core/NES/HdPacks/HdNesPack.cpp), [HdPackConditions.h](https://github.com/nesdev-org/MesenCE/blob/a60e79feb4d6dcced5922d636f9211837d01e381/Core/NES/HdPacks/HdPackConditions.h).

**SOURCE OBSERVATION — authoring/cost:** `HdPackBuilder::ProcessTile`, `GenerateHdTile` and `SaveHdPack` collect/deduplicate tile variants, generate editable imagery and write pack metadata, including supported-ROM identity. Frame buffers, owned tile data, PNG initialization and rule evaluation have costs; no benchmark was obtained. The legacy documentation warns that high scales cost performance. Context rules are game-specific authored knowledge; optional patch/changed-sprite-limit features are distinct from passive replacement and must not be imported as a fidelity-preserving default. See [HdPackBuilder.cpp](https://github.com/nesdev-org/MesenCE/blob/a60e79feb4d6dcced5922d636f9211837d01e381/Core/NES/HdPacks/HdPackBuilder.cpp).

**GTC-HD INFERENCE — consequence:** start with a capture-bound selection, not a purported universal tile/entity identifier. Persistent replacement would first require immutable graphics/palette content, declared rule precedence, contextual matching and invalidation evidence. Recording enough information for original rendering and author inspection is more useful than merely enlarging a hash key.

### C. PPSSPP: cache identity and authored replacement identity need different stability

**DOCUMENTED CLAIM:** the [texture-replacement reference](https://www.ppsspp.org/docs/reference/texture-replacement/) describes dumping decoded textures, editing images and mapping them through `textures.ini`. It recommends ignoring addresses for many packs and explains palette/hash-range complications. Address, palette and content each convey different information; more fields do not automatically yield a better authored selector.

**SOURCE OBSERVATION — producer/lookup:** `TextureReplacer::ComputeHash` hashes relevant texture bytes with configurable range/stride handling. `FindReplacement` uses an internal cache key but can remove addresses specifically for file lookup. `LookupWildcard` tries progressively broader aliases; an empty alias explicitly ignores replacement. `NotifyTextureDecoded` provides the original decoded image for saving. `NotifyConfigChanged` reloads game-specific configuration and clears replacement state. See [TextureReplacer.cpp](https://github.com/hrydgard/ppsspp/blob/d2ea558e4924b03dcbe13ae1c85ee4b7a750d8dd/GPU/Common/TextureReplacer.cpp), [TextureReplacer.h](https://github.com/hrydgard/ppsspp/blob/d2ea558e4924b03dcbe13ae1c85ee4b7a750d8dd/GPU/Common/TextureReplacer.h).

**SOURCE OBSERVATION — consumer/invalidation:** `TextureCacheCommon` incorporates texture address/dimensions and CLUT context, hashes content, and marks overlapping entries for recheck in `Invalidate`. `FindReplacement`/`PollReplacement` distinguish pending and active results. `PrepareBuildTexture` sets replacement use only for an active replacement; otherwise original decode remains available. Caches, pending work and decoded GPU textures survive across draws until revalidation/eviction/configuration boundaries. This trace is not a claim that every invalidation API clears everything: `InvalidateAll` is a no-op at this revision. See [TextureCacheCommon.cpp](https://github.com/hrydgard/ppsspp/blob/d2ea558e4924b03dcbe13ae1c85ee4b7a750d8dd/GPU/Common/TextureCacheCommon.cpp).

**GTC-HD INFERENCE:** address helps distinguish simultaneous storage uses but can break matching after relocation. Palette helps distinguish recolors, while irrelevant palette entries can destabilize an otherwise unchanged asset. Content can survive relocation but alias different roles. A frame/fetch token identifies an occurrence, not a persistent asset. Broader wildcard/range rules improve reuse only by accepting more ambiguity. None of these tradeoffs is solved by concatenating all fields.

No game patch is intrinsic to this texture mechanism; packs and exceptional hash ranges can require game-specific knowledge. Loading/decoding and polling budgets are visible in source; no startup/runtime measurement was made. PSP texture boundaries, CLUT data and GPU draw lifetimes are not available merely from SNES final winners. **Consequence:** keep source evidence, ephemeral cache keys and authored matching policy conceptually separate; defer persistent matching until it has real mutation/relocation witnesses.

### D. RT64: transfer the inspect/replace loop, not N64 geometry assumptions

**DOCUMENTED CLAIM:** the pinned [texture-pack guide](https://github.com/rt64/rt64/blob/43373749dac9bbc1b653e6a02aed40a9e1783bed/TEXTURE-PACKS.md) describes creator inspection, replacement files, `rt64.json` and stream/preload/stall choices. It is an integration guide, not proof that every host application exposes an identical Studio.

**SOURCE OBSERVATION — creator/producer:** the inspector can pause rendering, select a draw call's tile, choose a replacement within the pack directory and save the association. `queueGPUUploadTMEM` copies texture-memory bytes and relevant tile/dimension/palette state into queued work. `TMEMHasher::hash` version 5 hashes interpreted rows and relevant TLUT entries with format/dimension context. Owned queued bytes avoid interpreting later mutated TMEM as the original upload. A texture hash is still not a scene-object identity. See [rt64_debugger_inspector.cpp](https://github.com/rt64/rt64/blob/43373749dac9bbc1b653e6a02aed40a9e1783bed/src/gui/rt64_debugger_inspector.cpp), [rt64_texture_cache.cpp](https://github.com/rt64/rt64/blob/43373749dac9bbc1b653e6a02aed40a9e1783bed/src/render/rt64_texture_cache.cpp), [rt64_tmem_hasher.h](https://github.com/rt64/rt64/blob/43373749dac9bbc1b653e6a02aed40a9e1783bed/src/common/rt64_tmem_hasher.h).

**SOURCE OBSERVATION — consumer/lifetime:** `addResolvedPaths` searches replacement databases and can calculate older hash versions from owned data. `uploadThreadLoop` handles streamed versus immediately loaded replacements and optional cached low mips. `TextureMap::use` selects replacement state only when enabled and present; otherwise it retains the original texture's dimensions/state. `reloadReplacements` revisits loaded textures after edits; cache eviction and references manage longer-lived allocations. This is a focused cache/selection trace, not a complete audit of every backend's draw submission.

**DOCUMENTED CLAIM / GTC-HD INFERENCE:** streaming trades delayed/pop-in replacement for lower up-front loading; preload trades startup/memory for readiness; stalling can interrupt presentation. Low-mip caches mitigate some transitions without making memory free. No timings were measured. Pack authors can work with captured textures without changing game logic, but renderer integration and N64 tile/draw-call state are prerequisites. SNES winner provenance supplies neither N64 geometry nor physical depth. **Consequence:** first prototype the small select/inspect/edit/preview loop with ready, immutable inputs and an original fallback. Pack streaming, geometry-based selection and a sharing service can wait.

### E. Libretro Slang: separate pass scales, formats and meaning

**DOCUMENTED CLAIM:** the [official Slang shader/preset specification](https://docs.libretro.com/development/shader/slang-shaders/) describes pass-specific sizing, filtering, formats, parameters and composition. This is Libretro's preset/shader system, not another language/project named Slang.

**SOURCE OBSERVATION:** despite its filename, [dual_filter_2_pass.slangp](https://github.com/libretro/slang-shaders/blob/1e0238f9fdd4668ce8212c31d80877af605d3b53/blurs/dual_filter_2_pass.slangp) declares four passes: linearize, downsample, upsample and delinearize. It specifies float intermediates, different filtering/wrap policies, half-size downsampling, double-size upsampling and viewport presentation. `downsample.slang` and `upsample.slang` consume the previous pass via `Source` and derive tap offsets from source dimensions and `BLUR_RADIUS`; parameters are declared separately. This selected effect has no temporal history or asset matching. See [downsample.slang](https://github.com/libretro/slang-shaders/blob/1e0238f9fdd4668ce8212c31d80877af605d3b53/blurs/shaders/dual_filter/downsample.slang), [upsample.slang](https://github.com/libretro/slang-shaders/blob/1e0238f9fdd4668ce8212c31d80877af605d3b53/blurs/shaders/dual_filter/upsample.slang), [parameters.inc](https://github.com/libretro/slang-shaders/blob/1e0238f9fdd4668ce8212c31d80877af605d3b53/blurs/shaders/dual_filter/parameters.inc).

**GTC-HD INFERENCE:** the author tunes a preset and shader parameters, not game execution. Intermediate images/taps cost bandwidth and storage; no measured budget follows from this source. Resize invalidates image dimensions, not persistent asset identities. Missing-shader/compile-failure recovery belongs to the frontend and was not verified here; a GTC-HD original bypass must be specified independently. Color-only postprocessing cannot recover provenance, hidden objects or depth. The example's [2.2-power linearization](https://github.com/libretro/slang-shaders/blob/1e0238f9fdd4668ce8212c31d80877af605d3b53/blurs/shaders/kawase/linearize.slang) and [inverse](https://github.com/libretro/slang-shaders/blob/1e0238f9fdd4668ce8212c31d80877af605d3b53/blurs/shaders/kawase/delinearize.slang) are not an established SNES display model.

**Consequence:** keep native artwork sampling, categorical semantic masks, a smooth effect field and final viewport scaling separate. Nearest sampling may preserve art/mask boundaries while a light/glow field uses a different resolution/filter/format. Do not bilinearly interpolate source IDs, or choose 8x for every buffer because another demonstration used it. This lesson does not select Libretro, a graphics API or production shader format.

There is no public capture, matcher, renderer, fallback or invalidation implementation to trace.

Unpublished internals do not block this build.

### G. Brief contrast: application-owned enhancement versus universal capture

**DOCUMENTED CLAIM:** [snesrecomp's README](https://github.com/RetroPortingToolKit/snesrecomp/blob/88a9f7f51be3b1f0a805821e0fff7aa6f9e2246e/README.md) describes per-game analysis/configuration/integration and validation, not a drop-in universal enhancement path. [StarFoxSNESRecomp's README](https://github.com/mstan/StarFoxSNESRecomp/blob/589c09991b8b38a752b0abdf86bb169de31f200b/README.md) describes a development reference and credits `kandowontu/starfox-enhanced` as the authoritative port reference and origin of the custom renderer. This audit preserves that attribution rather than attributing all rendering work to the wrapper project.

**SOURCE OBSERVATION:** `StarFoxPresentationCaptureLine` stores per-line state and takes a PPU snapshot; `StarFoxPresentationRememberStock` retains native presentation. `StarFoxEnhancedRenderFrame` checks capture readiness and game-specific scene/memory conditions, invokes enhanced rendering where supported, and has `NotHandled`/stock-center fallback paths when disabled or unsupported. Scene-specific geometry, game addresses and retained snapshots supply meaning unavailable from arbitrary SNES pixel winners. This establishes explicit boundary/fallback code, not identical native behavior for all enhancement options. See [starfox_presentation.c](https://github.com/mstan/StarFoxSNESRecomp/blob/589c09991b8b38a752b0abdf86bb169de31f200b/src/starfox_presentation.c), [starfox_enhanced_renderer.c](https://github.com/mstan/StarFoxSNESRecomp/blob/589c09991b8b38a752b0abdf86bb169de31f200b/src/starfox_enhanced_renderer.c).

**GTC-HD INFERENCE:** authoring here includes game-port/code integration; it is not a reusable texture-rule workflow. Changes are recognized through explicit game state and new captures, not a general persistent matcher. Costs and general compatibility were not measured. Transfer the application-owned original/enhanced boundary and retained fallback; defer assumptions based on known game geometry. No CPU-recompiler audit or game-port recommendation follows.

## 4. What can GTC-HD actually transfer now?

These are **GTC-HD INFERENCE / PROPOSED EXPERIMENT**, not selected formats. Native source provenance identifies an observed producer; composition and arithmetic describe participation; persistent asset/entity identity is a different problem. Physical depth/emission would be authored or inferred interpretation. Renderer policy decides how to use those facts. BG priority is not depth, brightness is not emission, and OAM slot reuse is not object continuity.

| Technique / intended benefit | Required inputs | Already available in GTC-HD evidence | Missing or ambiguous inputs | Faithful fallback | Smallest useful validation | Priority for first prototype |

### Recommended build: bounded replay and source-aware glow preview

**PROPOSED EXPERIMENT:** a small consumer loads retained evidence, displays an owned native crop, lets the author inspect a contributing source occurrence, and previews adjustable glow strength/radius around that occurrence's contribution mask. It is a frozen authoring interaction, not live emulation. Glow is an explicitly authored aesthetic choice; it is not inferred physical emission, a depth claim or a demonstration of shadows.

**Minimum contract and ownership:** approve a contiguous active, lowres, noninterlaced tiled-BG/OBJ interval within one native raster period, with an explicit crop and store-slot/destination mapping. Bind the import manifest to capture SHA-256, producing source commit/schema, epoch, sequence bounds, relative frame/field and supported modes. Resolve aliases and distinguish presentation destinations from retained backing; do not treat two sample descriptions as two independent physical writes. Exclude borders/clears/other-field data not owned by the interval. Unowned pixels must be visibly outside the claimed crop, not silently filled and called reconstructed. Reuse of retained inputs needs approval of scope; this does not select a showcase game or run a new ROM.

**Initial state and independent reconstruction:** start from a documented native scanline seed or an explicit captured boundary snapshot whose origins are understood. Preserve sample order and native state lifetimes; reject discontinuities or unavailable carried history. Read captured raw winner colors, operand scalars and controls, independently determine/verify operand choice, clipping, operation, half behavior and brightness/channel conversion, then calculate the native result. The captured `preBrightness` and `stored` values are comparison references only, never replay outputs copied as the answer. Captured before/after Math snapshots can validate state evolution, not replace it. Fixed-color scalar input is legitimate captured input; a captured blended result is not. This reconstructs the already selected sample, not unseen BG/OBJ competition or a scene from original graphics assets.

The first real-capture slice can honestly cover NoMath, CurrentSub and FixedColor addition already observed. If hires/carry, subtraction, halving or other unimplemented paths occur, leave them in reference view and mark replay/enhancement unsupported. Generalizing those paths is a later requirement, even though host evidence already exists. A crop with incomplete initialization/ownership fails import rather than guessing history.

**One interaction:** select a visible pixel, inspect native source and actual arithmetic participation, then apply one capture-bound annotation to an explicitly shown set of source occurrences. Main and CurrentSub participation must follow the consumed controls; a FixedColor fallback must not falsely select the sub winner, and a clipped/skipped source must not be claimed as contributing. Participation is a diagnostic membership mask, not a measurement of physical energy. Token/source grouping must expose its selected extent; it must not silently claim a whole sprite, entity or asset. The annotation contains only enough selection and effect parameters for this task and is bound to the exact capture/epoch. A mismatched capture or unknown source produces no effect. With no annotation, native/replay viewing and inspection still work; universal automatic enhancement is not demonstrated by this authored slice.

**Views and fallback:** provide Original/Reference, independently Replayed, Enhanced, and a replay-difference view for the same owned crop. Recorded final colors may populate Original/Reference and unsupported-path fallback, clearly labeled as such. Enhancement is permitted only after replay validates its underlying owned samples. Strength zero and disabling enhancement must restore the reference exactly before optional display conversion. Do not borrow unsupported pixels from later mutable emulator state.

**Sampling policy:** preserve native artwork and categorical mask boundaries; calculate the smooth glow field separately; compose and scale for the final viewport explicitly. A mask identifies sources, so interpolation must not invent intermediate source IDs. No particular API, shader language, working multiplier, HDR transfer function or final renderer architecture is selected. Numerical native validation occurs before display processing.

### Acceptance criteria

All criteria are future validation requirements, not results of this audit.

1. **Owned import:** exact input identity, supported interval, crop, seed/history and store mapping are inspectable. Missing/corrupt records, wrong capture identity, unknown origins, discontinuities and unsupported ownership are rejected or visibly excluded. No complete-frame claim follows from callback count.
2. **Independent native equality:** every supported owned sample matches captured RGB555 after independent arithmetic and brightness conversion. Report counts for NoMath, CurrentSub and FixedColor witnesses, including their nonzero second operands where present. Deliberately altered operand/control inputs must change the calculated result or trigger a consistency failure; copying reference colors cannot satisfy the check.
3. **Honest selection:** show the exact participating source occurrences and explain main/sub/fixed fallback. Unknown, clipped, skipped or unconsumed sources cannot silently become emitters. No OAM/entity/depth inference is presented as native evidence.
4. **Useful reversible preview:** selection plus strength/radius changes yields a visible, restrained enhancement; Original and zero strength restore the same reference crop. Save/reload of the single annotation reproduces the preview only for its exact bound capture. No annotation is required for original viewing.
5. **Measured limits:** record import time, peak/retained memory and preview latency at the approved sampling configuration. Report CPU/GPU/backend conditions where relevant. These measurements characterize only this prototype; they do not establish live throughput, universal compatibility or production suitability.

**Non-goals:** complete scene reconstruction, independent tile decoding, persistent assets/entities, general profiles, a full Studio, community hosting, live capture/handoff, physical shadows, Mode 7 enhancement, temporal interpolation, all-game compatibility, production optimization or final core/API/language/schema acceptance. No emulator changes are proposed as part of the initial consumer merely to make missing evidence appear available.

### Actual blockers versus later gaps

The first build needs an agreed **ownership/initial-state/import contract** and access to the retained evidence identified by EXP-004's reported hashes. The report establishes the capture's existence and semantics; this audit did not revalidate private artifact integrity or build a consumer. Artifact availability/hash/schema verification is the first implementation prerequisite. If the chosen crop cannot be owned or initialized from those records, narrow it or request one specifically justified capture addition; do not invent a full-frame model.

Xavier must approve the bounded build, retained input scope, temporary implementation language/API if needed, annotation representation and trial sampling settings. These choices remain reviewable prototype decisions, not automatically permanent architecture. Core selection, a showcase game and a production profile schema need not be resolved to approve this offline experiment.

Complete graphics bytes, persistent identity, Mode 7, physical depth, live scheduling and untested commercial-ROM arithmetic paths do **not** block the proposed restricted slice. They become blockers only when a chosen consumer promises those capabilities. PixelRamp source publication is not a prerequisite.

## 6. Five prioritized lessons and three follow-up tasks

**GTC-HD INFERENCE — prioritized lessons:**

1. **Own the data and its lifetime before enhancing it.** Mesen/RT64 snapshots and bsnes-hd flush ordering show why a provenance token alone cannot replace immutable inputs or a synchronization contract.
2. **Separate occurrence, asset and entity identity.** PPSSPP/Mesen matching tradeoffs support a capture-bound selector now; they challenge the assumption that a larger composite key automatically solves persistence.
3. **Keep native facts, authored interpretation and fallback explicit.** An author may declare glow; the capture does not establish emission or depth. Original/reference recovery is a required consumer behavior.
4. **Make the next consumer expose its own missing data.** Replay plus one frozen visual interaction answers more than another broad audit, while avoiding premature live/frame/Studio commitments.
5. **Budget art, masks, effects and presentation separately.** Libretro's pass composition supports independent sampling policies; it does not justify scaling every diagnostic buffer or choosing 8x.

**PROPOSED EXPERIMENT — no more than three follow-up tasks:**

1. Review this recommendation and approve a short experiment specification covering ownership, initialization, supported interval, source selection, fallback and temporary implementation choices; verify the retained artifact identity as an input prerequisite.
2. Implement and validate the one offline replay/preview build under a separate explicit authorization, against the five criteria above. Keep the authored annotation local and capture-specific.
3. Use its observed failure or next consumer requirement to authorize **one targeted extension**: for example a deterministic hires/history ownership witness, or a bounded live handoff. Do not bundle Mode 7, persistent matching, depth and Studio into that extension without evidence that they are needed.
